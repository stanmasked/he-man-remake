# Stage174 — original app tick accumulator and fixed-delta interaction

Stage173 identified two independently verified original executable facts:
the handler passes fixed float32 0.04f into gameplay, and the app timer is
configured nominally for 60 callbacks per second. Stage174 models the
separate wall-clock accumulator between those callbacks and SpritePlayer.

## Recovered accumulator decisions

Private ARMv7 control-flow inspection of GSAppDelegate::onTick shows:

- It measures wall-clock elapsed time in integer milliseconds and adds
  that delta to a persistent accumulator.
- Before dispatching game updates, accumulated time is capped at **66 ms**.
- If the accumulator is below **16 ms**, no gameplay update runs yet.
- Otherwise, the loop consumes complete **16 ms** quanta, running one
  Kernel::tick per quantum, until fewer than 16 ms remain.
- Because the accumulator is capped at 66 ms, one callback can run at
  most **four** game updates; excess elapsed time beyond the cap is dropped.
- Each such Kernel::tick receives the separate fixed **0.04f** argument
  established in Stage173. At the default SpritePlayer rate, that input
  becomes 40 integer animation-time units.

This is the observed algorithm, not a claim that it is the intended
speed or that a real device delivers perfectly regular callbacks.

## Deterministic source-free model

- native/include/heman_app_tick_scheduler.h
- native/src/heman_app_tick_scheduler.c
- native/tests/test_app_tick_scheduler.c
- native/tests/test_sprite_timing_integration.c

The new bounded C99 function receives a fabricated wall-clock delta and
the saved accumulator remainder, then returns the number of 16-ms update
quanta and the new remainder. It uses no allocations and fails closed on
negative deltas or invalid state. Both GCC and Clang execute the same
fabricated tests through native/run_tests.sh.

A synthetic one-second schedule with 60 callback deltas patterned as
20 × 16 ms and 40 × 17 ms totals exactly 1000 ms. The accumulator emits
62 updates with 8 ms left over. At 40 units per update, the scheduler
*offers* 2480 units of player time over that interval if an animation is
still active. The finite two-play test animation itself reaches its
strict finished state after 37 updates and then holds, so its state does
not accumulate the remaining offered time. This shows the apparent
2.48× update/time-input ratio **while active**, not a benchmark of a
running original device. The 66-ms cap also means large stalls
intentionally discard some elapsed wall time.

## Synthetic Switch probe

The isolated asset-free NRO now uses the same C99 accumulator and sprite
clock modules. It feeds a repeatable 16,17,17-ms callback pattern to model
a nominal 60-Hz timer after integer-millisecond sampling, then performs
as many 0.04f player updates as the accumulator requests. A small HUD bar
shows the number of simulation updates generated by the current callback.
This is deterministic simulation input, not a measurement of the NRO's
actual wall-clock runtime.

The existing game NRO and main branch remain unchanged. No original IPA,
machine-code bytes, resources, animation records or private traces are
uploaded to public GitHub.
